01 · 知识生成 · 落地方案

对应蓝图 §2。本文解决：知识从哪里来？怎么产生？产生什么格式？

状态：草案（D2.3 / D2.4 / D3.3 / D3.4 / D3.5 / D4.2 / D4.3 / D5.2 / D5.3 待确认，见 §11）
前置依赖：无（生命周期起点）
关联文档：02-知识验证（AI 审核门控）· 04-知识存储（元数据 Schema 与条目模板）· 06-知识维护与治理（漂移判定）

1. 定位与边界

本方案采用 Qoder 中心化生成架构——所有知识生成均通过 Qoder 在开发者日常工作流中完成，不依赖独立的生成 Pipeline。Qoder 在三种场景下产生知识：SDD 流程产出设计知识、编码过程中检测知识漂移并更新、权威事实源变更时提醒开发者同步知识。

2. 生成架构总览

核心原则：

  • 知识生成嵌入开发者已有工作流，不额外派发写作任务
  • 所有产出均为 status: draft，须经 §4 知识审核后方可转 active
  • 知识条目与代码变更在同一 MR 中提交，保证知识随代码同步演进

3. 路径 1：SDD 流程生成

3.1 触发时机

在 SDD 工作流（java-backend-dev-guide §1）的需求分析和概要设计阶段，Qoder 自动识别当前任务是否涉及以下场景：

场景知识产出触发条件
新功能设计架构决策记录（Decision）涉及 3+ 文件或公共契约变更
接口契约变更接口知识条目（Contract）新增/修改 HTTP/RPC 接口
数据模型变更表结构知识条目（Contract）新增/修改数据库 Migration
配置项变更配置知识条目（Procedure）新增/修改 application.yml（配置中心见 D3.5，P0 不覆盖）
业务规则变更业务规则知识条目（Policy）涉及状态机、领域规则调整

3.2 生成流程

1. Qoder 检测到 SDD 场景（匹配 jbdg §6.1 路由表 #1 或 #2）
2. 加载 sdd-guide.md，产出 spec.md / plan.md
3. 识别涉及的知识类型（上表匹配）
4. 在 docs/sdd/{需求ID}--{特性}/ 下产出设计文档
5. 同时生成知识草稿到 _drafts/{module}/{topic}.md
6. 知识草稿遵循蓝图 §5.5.1 模板

3.3 知识草稿存放

草稿统一存放于仓库内 _drafts/ 目录（与代码变更同 MR 提交）：

_drafts/
├── {module}/
│   ├── {topic}.md          # 知识草稿
│   └── ...

草稿 frontmatter 标记 status: draft，CI 校验通过后由 Owner 审核决定是否转 active。

3.4 关键决策点

#决策已确认说明
D1.1SDD 场景识别方式✅ 混合识别（D）同时使用规则匹配（文件路径/注解）和 AI 判断（需求语义）
D1.2知识条目模板✅ 复用蓝图 §5.5.1不另建模板，SDD 产出直接套用
D1.3草稿存放位置✅ _drafts/ 目录与代码变更同 MR，不单独开分支
D1.4草稿与代码变更的关系✅ 同一 MR 提交保证知识随代码同步，不产生滞后

4. 路径 2：编码 + 漂移检测生成

4.1 触发时机

在编码阶段，Qoder 检测到以下情况时触发知识更新：

检测信号知识影响处理方式
修改了已有 API 签名对应知识条目可能过期标记 drift_detected，生成更新草稿
修改了配置项默认值配置知识可能过期同上
删除了已有代码符号引用该符号的知识失效标记高优先级漂移
新增了公共接口可能需要新增知识条目生成候选草稿

4.2 漂移检测机制

采用 source_uri 映射（主）+ 启发式规则（辅） 双层检测。

与蓝图 §7.4 的分工：本节是编码时本地即时提示（在开发者还持有上下文时给出，成本低、可立即修正）；蓝图 §7.4.3 是每日 CI 兜底对账（覆盖本地被绕过、历史条目、跨仓变更）。两者共用同一套 source_uri 映射语义，但只有 CI 侧有权写 flags。

性质：本地/CI 双层分工为工程推导；下方启发式规则为自拟（无外部依据，误报率待实测） | 置信度：中

第一层：source_uri 精确映射

# 伪代码：基于 source_uri 的漂移检测
for entry in knowledge_entries(status == active):
    source_path = resolve(entry.source_uri)  # gitlab:// → 本地路径
    if source_path in changed_files:
        # 源文件发生了变更，需要检查知识是否仍然有效
        if has_semantic_change(source_path, entry.knowledge_type):
            # 本地不写 entry.flags：蓝图 §7.4.1 规定 flags 由 CI 写入、人工不得手改。
            # 本地若写回，编码 MR 就要顺带修改知识条目 frontmatter，
            # 而跨仓写回路径（知识在哪个仓、走哪个 MR、谁审）未定义。
            # 本地只产出提示与更新草稿；flags 落库由蓝图 §7.4.3 每日定时任务承担。
            report_drift(entry, source_path)
            generate_update_draft(entry, source_path)

第二层：启发式规则（回落）

当知识条目缺少 source_uri 或源文件路径无法解析时，使用以下启发式规则：

启发规则检测方式
模块名匹配知识标题含模块名，且该模块有代码变更
符号引用匹配知识正文引用了 ClassName#methodName，且该方法被修改
配置前缀匹配知识涉及某配置前缀，且该前缀下的值被修改

4.3 关键决策点

#决策已确认说明
D2.1漂移检测主机制✅ source_uri 映射精确匹配，误报率低
D2.2漂移检测辅机制✅ 启发式规则覆盖 source_uri 缺失的历史条目
D2.3检测到漂移后的行为待确认选项：A) 自动标记 + 生成草稿；B) 仅标记，由开发者决定是否更新
D2.4启发式规则的误报处理待确认选项：A) 误报也标记，Owner 审核时排除；B) 设置信度阈值，低置信度不标记

5. 路径 3：权威源变更生成

5.1 设计约束

团队使用 Qoder 企业版本地安装，GitLab Webhook 无法直接触达开发者本地机器（NAT 穿透问题）。因此 不采用 Webhook 被动触发，改为 pre-commit hook 主动检测。

5.2 触发机制：pre-commit hook

5.3 检测范围

权威源类型检测路径模式对应知识类型
Swagger/OpenAPI**/openapi.yaml、**/swagger.yaml、**/api-docs/**Contract（HTTP 接口）
Flyway Migration**/db/migration/**/*.sqlContract（表结构）
SpringBoot 配置**/application*.yml、**/application*.propertiesProcedure（配置项）
配置中心声明**/bootstrap*.yml 中的配置中心引用Procedure（配置项）

5.4 hook 脚本实现

#!/usr/bin/env python3
"""pre-commit hook：检测权威源文件变更，提醒开发者更新知识"""

import subprocess
import sys
import re

# 权威源路径模式
# git diff --name-only 输出的是仓库相对路径，根目录文件无前导斜杠，
# 因此每个模式都要允许「根目录」与「子目录」两种形态
AUTHORITATIVE_PATTERNS = [
    re.compile(r'(^|.*/)openapi\.ya?ml$'),
    re.compile(r'(^|.*/)swagger\.ya?ml$'),
    re.compile(r'(^|.*/)api-docs/.*'),
    re.compile(r'(^|.*/)db/migration/.*\.sql$'),
    re.compile(r'(^|.*/)application.*\.yml$'),
    re.compile(r'(^|.*/)application.*\.properties$'),
    # bootstrap*.yml（配置中心引用）：D3.5 推荐 C（P0 不覆盖配置中心）确认后应移除此行，
    # 否则 hook 会对无法闭环的变更发出提醒
    re.compile(r'(^|.*/)bootstrap.*\.yml$'),
]

def get_staged_files():
    result = subprocess.run(
        ['git', 'diff', '--cached', '--name-only'],
        capture_output=True, text=True
    )
    out = result.stdout.strip()
    return out.split('\n') if out else []

def check_authoritative_changes():
    staged = get_staged_files()
    changed = []
    for f in staged:
        for pattern in AUTHORITATIVE_PATTERNS:
            if pattern.match(f):
                changed.append(f)
                break
    return changed

def has_knowledge_update():
    """暂存区是否已包含配套的知识变更。有则放行——否则开发者
    补完草稿再提交时，权威源文件仍在暂存区，hook 会二次阻断，
    唯一逃逸方式是 --no-verify，闭环在工程上走不通。"""
    staged = get_staged_files()
    return any(f.startswith('_drafts/') or f.startswith('docs/knowledge/')
               for f in staged)

def main():
    changed = check_authoritative_changes()
    if not changed or has_knowledge_update():
        return 0

    print("\n" + "=" * 60)
    print("[知识库提醒] 检测到权威源文件变更：")
    for f in changed:
        print(f"  - {f}")
    print()
    print("请在提交前使用 Qoder 执行知识更新：")
    print("  /update-knowledge")
    print()
    print("或跳过此检查：")
    print("  git commit --no-verify")
    print("=" * 60 + "\n")

    # D3.3 推荐 B（仅提醒）：return 0；若确认 A（阻断）改为 return 1。
    # 注意：无论选哪个，--no-verify 都能无条件绕过 pre-commit hook，
    # 阻断模式只提高摩擦，不构成强制力。真正的兜底在 CI 侧（蓝图 §7.3）。
    return 0

if __name__ == '__main__':
    sys.exit(main())

5.5 Qoder Skill：/update-knowledge

开发者收到 hook 提醒后，在 Qoder 中执行 /update-knowledge，Skill 负责：

  1. 读取 git diff --cached 获取权威源变更内容
  2. 按源类型分发解析：
    • OpenAPI 变更 → 解析接口签名差异，更新对应 Contract 知识
    • Flyway SQL 变更 → 解析 DDL 差异，更新表结构知识
    • application.yml 变更 → 解析配置项差异，更新配置知识
  3. 生成或更新 _drafts/{module}/{topic}.md
  4. 将草稿 git add 到暂存区，允许开发者一次提交

5.6 关键决策点

#决策已确认说明
D3.1触发机制✅ pre-commit hook解决本地 Qoder 无法被 Webhook 触达的问题
D3.2权威源检测范围✅ openapi + flyway + application.yml覆盖 API/数据库/配置三类核心权威源
D3.3hook 行为待确认选项：A) 阻断提交；B) 仅提醒。当前脚本按 B 实现（return 0），确认 A 只需改最后一行返回值。注意两种模式都可被 --no-verify 绕过
D3.4知识更新时机待确认选项：A) 必须同一次提交包含知识更新；B) 允许后续单独提交知识更新
D3.5配置中心知识待确认配置中心的配置项如何同步到知识库？选项：A) 导出为 application.yml 格式统一管理；B) 单独维护配置中心知识条目；C) P0 不覆盖配置中心，仅覆盖本地配置文件

6. 知识条目标准

6.1 条目结构

每条知识必须包含以下要素（对应蓝图 §2.4）：

要素要求说明
背景必须为什么需要这条知识？不写会出什么问题？
方案必须技术方案的准确陈述，引用具体代码位置
正反例必须正确做法 + 错误做法 + 解释为什么
权威源绑定必须source_uri + source_revision（frontmatter）
Owner必须owner_group（frontmatter）
适用范围建议涉及哪些模块、服务、API
知识类型必须frontmatter knowledge_type（蓝图 §5.2 的 7 字段之一），枚举即 §6.2 的七类。必须是写入时采集的必填字段而非派生字段：分级复核周期、漂移语义过滤、主张抽取范围都以它为输入

6.2 知识类型分类

类型说明典型来源

Decision架构决策记录（ADR）SDD 流程的 plan.md

7. 多源解析与预处理

7.1 P0 范围：仅 Git 仓库 Markdown

P0 阶段只处理已经在仓库中以 Markdown 形式存在的知识，以及通过权威源自动解析生成的结构化知识。

7.2 P1 范围：外部来源接入

来源解析方式产物失真风险
Confluence / WikiREST API 导出 XHTML → 转 MarkdownMarkdown + 页面版本号宏、附件、页面树层级丢失
PDF版面解析（保留标题层级）Markdown + 页码锚点表格与多栏版面极易错序

7.3 解析失败处置（Fail-Closed）

失败类型处置是否入库
解析器抛异常 / 超时记录 parse_failed，告警 Owner否
解析成功但标题层级为 0标记 structure_degraded，进入人工确认队列否，待人工
