1. 定位与边界

度量评价与落地路径是整套方案的"总控塔"：它不解决具体技术细节，只解决建设顺序、组织分工、验收标准、非功能性约束四件事。

与 01–08 的关系：01–08 分别解决知识生命周期的八个阶段，本文解决"这八个阶段按什么顺序建设、谁来建设、建到什么程度算完成"。

2. 核心设计决策

2.1 成熟度模型：L0–L5

蓝图 §10.1 定义六级成熟度，安全不是最后阶段的能力：

阶段建设目标主要能力该阶段必须同时具备的安全与审计能力
L0可搜索聚合知识、目录、基础检索classification 字段落库；检索前按密级过滤（05 §9.1）
L1可溯源来源、版本、Chunk 引用、拒答检索审计日志开启；引用可解析率可统计
L2可治理Owner、生命周期、漂移治理越权访问告警；Owner 变更留痕
L3可约束Hook、Lint、测试、CI 门禁阻断事件全量留痕并可回溯到 trace_id
L4变更驱动MR、API、DDL 自动影响分析影响分析结果纳入审计，供事故归因
L5持续自证评测、反馈、收益和熵治理评测集含权限越权集，回归门禁覆盖安全用例

为什么密级过滤属于 L0：一旦无过滤的知识先被 Agent 消费，事后补权限无法撤销已经泄露的内容。这是把 05 §9.1 的检索前密级过滤提前到 P0 的原因。

L0–L5 是能力累计层级，不是时间顺序，也不是「后一层可以晚做」的意思。三点必须澄清，否则该表会被误读为路线图：

  1. 高层级包含低层级的全部能力。L3「可约束」成立的前提是 L0 的密级过滤与 L1 的溯源仍然生效；任何一层退化都会使其上层失效（例如 L1 的引用不可解析，则 L3 的阻断事件无法回溯到 trace_id）。
  2. 层级与建设期（§3 的 P0–P3）不是一一对应。P0 就要求 L0 + L1 的安全与审计能力全部就位（见 §2.7.1 的 10 项硬门禁），而 L5 的评测能力排在 P2。用「我们现在才 L1」来解释「所以还不能上权限过滤」是本表最典型的误用。
  3. 表中「该阶段必须同时具备的安全与审计能力」列是准入条件，不是可选增强。某一层的建设项若不具备同层要求的安全能力，则该层不算达成——例如 L4 的影响分析若其结果不进审计，则 L4 未完成，不能记为已达成。

2.2 冷启动路径：C0–C3

蓝图 §10.1 明确先读后写原则——第一批价值来自让存量知识可检索，而不是让团队写新条目。

为什么不能先要求写作：写一条合格知识的成本落在作者身上，收益落在读者身上，而读者通常是未来的、不确定的、看不见的人（§3.2）。冷启动阶段就派发写作任务，收到的必然是凑数内容，而这些内容立刻成为 06 §2.4 定义的负价值知识。

四期推进：

期目标做什么明确不做什么对应建设期（§3）
C0a可检索（Git 来源）Git Markdown 摄入（01 §7.1）+ 元数据最小集由 CI 自动回填 + 只读检索上线不要求任何人写新条目；不建全量分类体系；不含 Confluence/Wiki/PDFP0
C0b可检索（外部来源）Confluence / Wiki / PDF / Office 解析链路（01 §7.2）+ 权威源绑定（01 §7.4）不做无权威源绑定的批量导入（fail-closed，01 §7.3）P1
C1有需求证据开启审计日志（05 §9.3），统计 refusal 与低召回 query，形成种子知识清单不靠"哪个团队愿意配合"选题P0（审计）→ P1（清单产出）
C2核心域跑通选 1–2 个种子域补齐知识，打通 Owner 复核与漂移告警闭环不追求覆盖率指标P1
C3规模化全量摄入、关系图谱（06 §3.4，图谱建模本身在 06 中无独立小节，见 §6.2 LD9）、评测回归门禁（07 §2.5）—P2（评测门禁）→ P3（图谱）

为什么把原 C0 拆成 C0a/C0b：原 C0 一行同时要求「Git Markdown 摄入」与「Confluence/Wiki/PDF 解析」都在冷启动首期完成，但 §3.2 明确把「Confluence / Wiki / PDF / Office 解析链路」排在 P1，理由是「存量知识主体，无此链路则知识库只覆盖新增部分」。同一份文档对同一件事给出两个不同的期次，是执行时必然产生分歧的地方——按 C0 读，P0 验收就应包含 PDF 解析；按 §3.2 读，P0 只需 Git 链路。

拆分的依据是两类来源的工程性质不同：Git Markdown 是零转换来源（文件本身即目标格式，CI 可直接读取 frontmatter 与 blob hash），而 Confluence/Wiki/PDF 需要解析服务、结构保留、权威源绑定与 fail-closed 处置（01 §7.2–§7.4），且 Confluence REST 返回的是 XHTML storage format，需要独立的转换与校验链路。把两者捆在一期，等于让 P0 的完成判据依赖一个 P1 才建成的组件。

「对应建设期」列是本次新增：原文 C0–C3 与 §3 的 P0–P3 是两套并行的阶段划分，却没有任何一处说明它们的对应关系。缺了这一列，「C2 阶段只采集不设目标」（§5）这类表述无法落到具体建设期，验收时也无从判定某个 C 期是否完成。对应关系为多对多（一个 C 期可跨多个 P 期），不是简单的一对一。
种子域选择判据（三条同时满足）：

  1. AI Coding 场景在该域的占比高。
  2. 该域有明确的 Owner 团队（否则 03 §3.1 的责任制无法落地）。
  3. 存量文档相对集中（解析成本可控）。

迁移顺序不按目录树，按 C1 的 query 命中缺口。按目录迁移的结果是：最容易迁的（格式规整的旧设计文档）先被迁完，而这些恰恰是查询最少、最可能已过期的部分。

2.3 冷启动常见反模式

反模式为什么会失败
先建全量分类体系再填内容分类体系会随实际内容变形，先建的必然返工，且返工期间目录不可用
先要求每团队交 N 篇交上来的是凑数内容；配额一旦达成，后续再无人主动写
先上 GraphRAG无实体无关系可抽取；L4 的变更驱动影响分析能力建立在 L0 的数据与 L1 的溯源之上，跳过前序层级时图谱无输入（§2.1）
把"存量迁移完成"当冷启动完成判据迁移完成只证明可搜索，不证明有人在用

冷启动完成判据：

  1. 审计日志中 refusal 率与低召回 query 数可统计（机制保证——只要有日志即成立）。
  2. 种子域的核心问题能引用回源（阈值待实测）。
  3. 主动提交信号成立：连续 4 周（周期待实测）内「非平台团队成员主动提交的知识 MR 数 > 0」且累计提交人数 ≥ 3（人数阈值待实测）。

为什么不是「至少一个人提交过一次」：那是一个二元事件（0 或 1），不是可看环比方向的量，不符合附录对「趋势指标」的定义；且 n=1 无统计意义——单次提交可能源于好奇或私人关系，不能证明激励结构跑通。改为「连续 N 周 + 人数 ≥ M」后既是趋势口径，也避免偶然性。

产生该事件的机制必须显式设计，否则判据不可达成：§2.4 原则 2 的自动转化草稿若由平台组的摄入链路提 MR，作者是平台组，不满足「非平台成员主动提交」；而 C0/C1 又明确不派发写作任务、不培训用户。唯一路径是「确认即提交」——见 §2.4 原则 5。

2.4 组织与角色：四类分工

蓝图 §10.2 定义四类角色，写作激励必须与阅读收益解耦：

角色职责归属兼任约束
知识 Owner单条目内容正确性、周期复核、漂移处理条目对应模块的负责团队不得为平台组——平台组不了解业务语义，代管等于无人负责
知识 Steward目录结构、受控术语表、条目模板、元数据 Schema 演进、CODEOWNERS 维护每租户各一套不得同时是该域的审批人，否则自审自批（03 §3.2）
平台组摄入链路、索引、检索服务、权限过滤、审计、评测流水线共享—
知识园艺周期扫描孤儿/过期/低边际价值条目，产出待处理清单平台组 Agent + 人工确认不得有自动删除权（06 §2.4 三重防误删）

激励不对称是知识库衰败的根因，不是"大家不重视"。四条设计原则：

  1. 不要把"写知识"当额外任务派发。派发出来的必然是凑数内容（§2.2）。

  2. 嵌进本来就要做的动作：MR 描述、ADR、事故复盘、评审结论由摄入链路自动转化为条目草稿（01 §7、02 §4.1），人只做确认与补充，不做从零写作。

  3. 收益必须回流到作者与团队两个维度：条目被检索命中次数、被 Agent 引用次数按作者个人与其 owner_group 双维度可见。数据源已存在——05 §9.3 的审计日志含 retrieved_chunks（命中）与 generated_claims（被引用），无需新增埋点，但聚合管道与看板需单独建设（工作量不可忽略，已计入 §2.6.6 治理人力）。

    • 原文只写「按 Owner 可见」不足以解决激励不对称：§2.3 的论证前提是「写作成本落在作者个人身上」，而 Owner 是团队（owner_group）。收益只聚合到团队维度，作者个人仍无收益，激励不对称未被消除。因此需要 frontmatter 新增 author 字段（个人，与 owner_group 并存）——该字段是否纳入 P0 Schema 见 §6.2 LD8。
    • 反博弈约束：命中次数只做团队级趋势展示，不做个人排名；单条目命中数须与 06 §2.4 的边际价值公式联立展示（避免只看分子不看分母）；明确不得作为绩效考核输入。否则可预见的博弈是拆条提高计数、把 owner_group 挂到高频域、堆砌热门关键词——这与原则 4「正向指标可被凑数刷高」是同一个问题。
    • 合规约束：看板只含聚合计数与 knowledge_id，不含 query_text 原文（05 §9.3 纪律 3：日志本身有密级）。

  4. 反向指标的凑数成本更高："因知识缺失导致的返工与事故"比"写了多少篇"更能说明价值，也更容易获得管理层持续投入。正向指标（篇数）可以零成本刷高；反向指标要压低则需隐瞒一次真实事故，而事故有独立上报渠道（安全/质量事件系统），因此反向指标的下限受外部系统约束。

    但这不等于反向指标不可操纵——它依赖归因，而 07 §2.3 规定归因是「AI 提议 + Owner 确认」，确认权在 Owner 手上，Owner 又恰是知识库质量的被考核方。若 Owner 倾向把失败归因为 Generation Failure（模型问题）而非 Business Understanding Failure（知识缺失），反向指标就被系统性压低。07 §3.2 的 Cohen's Kappa 只度量标注者之间的一致性，不度量系统性偏向（所有人都少标同一类时 Kappa 可以很高）。因此配套约束：

    • 归因确认人不得是该条知识的 Owner；Business Understanding Failure 的归因由 Steward 或第三方团队复核。
    • 每季度抽样 N%（待实测）的归因结论做盲评（标注者不知晓原结论），一致率低于门槛则触发归因指南修订。门槛见 §2.7.2「归因盲评一致率门槛」。

    性质：本条整段为工程推导，无外部量化依据（与蓝图 §10.2 同口径） | 置信度：中

  5. 确认即提交：原则 2 的自动转化草稿，必须由该域业务成员（而非平台组）在自己的分支上确认后以自己名义提 MR。草稿由机器生成，但 MR 的作者身份必须是业务成员——这是「主动提交」能被观测到的唯一路径。配套建设项：草稿确认入口（IDE 插件或 MR 模板一键确认），见 §3.2 P1。

2.6.1 容量与规模量级

性质：本条为工程推导，无外部依据 | 置信度：中

切分放大系数必须实测：一条知识条目按 04 §5.1 切分后产生的 chunk 数不是常数，它取决于文档长度分布。若按"1 条 = 3 chunk"估算而实际是 8，向量存储与 Embedding 成本会偏差数倍，且这个偏差在 P0 阶段就会暴露。

容量测算第一步：对现有语料做一次完整切分，统计 chunk 数分布（均值 / P90 / 最大值），再乘以上下文前缀带来的长度增量（04 §5.2）。

2.6.2 QPS 与并发

调用来源流量特征设计影响

关键判断：Agent 自动检索的量级通常远高于人的提问量级——一次编码任务可能触发数十次知识检索（「数十次」是定性量级判断，非实测值；该因子必须在 P0 按 §2.6.2 的测算方法实测后回填，性质为阈值待实测）。若按"团队人数 × 人均提问数"估算容量，会严重低估。容量必须按"并发 Agent 数 × 每任务检索次数"估算。

Agent 检索同样延迟敏感：Agent 在编码过程中检索是同步阻塞的——拿不到结果就无法继续生成。一次任务数十次检索，每次多等 300ms 就累积成数秒任务延迟。因此不能只把人的交互式提问纳入 P95 目标，否则会出现「容量按 Agent 负载设计（吞吐优先）、延迟按人的负载设计（P95 ≤ 500ms）」的分裂，两者在压测时必然冲突（高并发 P95 与低并发 P95 完全不同）。

2.6.2.1 流量优先级与限流

§2.6.4 的降级表只覆盖组件故障，未覆盖过载（检索服务被打满）。人的交互式提问与 Agent 批量检索竞争同一资源时必须有明确优先级：

优先级流量类型过载时处置
P1人的交互式提问永不拒绝，最多排队
P2Agent 编码中检索限流（按租户/会话配额），超限返回「暂不可用」而非空结果，使 Agent 知道自己没有知识（Fail-Closed）
P3CI / Hook 校验、索引构建与重建先排队、后暂停；重建可限流可暂停（§2.6.3 约束 1）

配额按租户归集（§2.5），这也是「审计与配额按租户核算」的用途之一。限流阈值待实测。

2.6.3 部署架构

三条架构约束：

  1. 摄入层与服务层资源隔离。索引重建是 CPU/GPU 密集操作，与在线检索争抢资源会直接击穿 P95。重建应能限流、可暂停。
  2. Embedding 服务是单点依赖，必须配熔断与降级（§2.6.4）。
  3. 审计日志独立存储，不与业务元数据同库（05 §9.3 纪律 1）。

2.6.4 高可用与降级策略

核心原则：知识库不可用时，Agent 必须知道自己"没有知识"，而不是继续凭记忆生成。这是 Fail-Closed 在系统层的体现（05 §9.2 OWASP 第 14 类威胁）。

故障降级行为用户可见结果
向量库不可用降级为 BM25 + Exact 双通道提示"语义检索暂不可用，结果可能不完整"
全文索引不可用降级为向量单通道，精确标识符查询直接拒答提示；标识符类问题不猜

关键取舍：权限与审计本地缓冲失败时继续服务，等于在无管控状态下输出高密级内容且无法追溯。可用性与合规冲突时，本方案选择合规。这个取舍必须写入方案并在评审时明确确认，不能留到故障时临时决定。

但「拒绝服务」不能直接挂在异地同步上：§2.6.5 要求审计日志 RPO 趋近 0（异地同步），而 05 §9.1 的检索延迟预算是 P95 ≤ 500ms。若异地同步是同步阻塞的，每次检索都要含一次跨地域写入，物理上很难满足 500ms；若是异步的，RPO 就不趋近 0。二者不可兼得，必须显式取舍：

本方案选择「本地 append-only 缓冲 + 异步异地上传 + 缓冲耗尽才拒绝服务」。这样既把「审计存储短时抖动」与「知识库不可用」解耦，又保持 RPO≈0（缓冲不丢，只是延迟落地）。判定口径随之明确：

情形是否算「写入失败」处置

  • 按天 + 按租户分区（append-only，天然可分区）
  • 冷热分层：热数据本地/同区，冷数据异地归档（§2.6.5）
  • 容量增长是无上界的（保留期由合规确定，通常数年不删），已单列入 §2.6.6 成本模型
  • 保留期到期后的合规删除流程须与 §2.7.2「审计日志保留期」衔接

可用性 SLO 与 RTO 目标：本节原无任何可用性数值。既然明确「可用性与合规冲突时选择合规」，就必须量化牺牲了多少可用性，否则该取舍无法在评审中被确认。建议目标（全部待实测）：检索服务可用性 ≥ 99.5%；审计缓冲耗尽导致的拒绝服务年累计时长 = 缓冲容量 / 平均写入速率 × 年故障次数（须实测后回填，并作为缓冲容量的选型依据）。

RPO / RTO 设定依据是"可重建性"而非"重要性"：

  • 向量与全文索引：RPO 无意义（可从 Git 完全重建），RTO = 04 §7 的索引重建时间。
  • 审计日志：RPO 必须趋近 0（仅追加、异地同步），因为不可重建。
  • 评测集：RPO = 0（Git 提交即备份）。
  • 元数据库治理状态：RPO = 快照间隔（建议 ≤ 1 小时，待实测；与审计日志的 RPO≈0 区分开），RTO = 快照恢复 + WAL 重放时间。若 04 §3.6 S1.5 选择「flags 写回 Git frontmatter」，则 flags/flagged_at 部分转为 RPO = 0，快照间隔可放宽。

关键取舍："索引不备份、只重建"是本方案的核心容灾策略——它把容灾问题转化为"重建够不够快"，从而让 04 §7 的索引重建时间从一个性能指标升级为容灾指标。若重建时间不可接受，才需要引入索引备份——顺序不能反。

这个取舍在大型档下有两个成立前提，缺一不可：

  1. 上下文前缀必须持久化。§2.6.6 指出前缀生成是「全量重建时最大的单项 token 消耗」，需为每个 chunk 调 LLM 一次。百万级 chunk 要在 30 分钟内跑完，意味着 ≥ 555 次 LLM 调用/秒——远超任何企业 LLM 网关的限流阈值，成本也不可接受。而 Prompt Caching 解决不了这个问题：它只能省掉输入 token 的重复部分（文档级上下文），输出 token（每个 chunk 自己的前缀文本）无法缓存，调用次数也无法减少。唯一可行解是把前缀结果持久化（随 chunk_hash 写入 Git sidecar 或元数据库），使重建时只对 content_hash 变化的 chunk 重新调用 LLM，全量重建退化为「Embedding + 索引写入」。若前缀不持久化，则本取舍在大型档不成立，必须回退为索引备份。

  2. 重建时长目标必须按规模档位分级。§2.7.2 原写「≤ 30 分钟」是一个与规模无关的常数，而 §2.6.1 明确规模分三档：大型档 = 百万级以上向量，30 分钟 = 1800 秒，要求 ≥ 555 chunk/秒的持续 Embedding 吞吐（还不含解析、切分、写入、ES 索引构建）。对千级和百万级都适用的重建时长目标在物理上没有意义——§2.6.1 已经对切分放大系数要求「必须实测」，同样的谨慎必须用在重建时长上。分级目标见 §2.7.2。

重建时长的推导公式（不写裸数字）：

重建时长 ≈ chunk 总数 / min(Embedding 吞吐, 索引写入吞吐)
         + 变更 chunk 数 × LLM 单次延迟 / LLM 并发度

各项均为待实测。

与 04 §8 的口径统一：04 §8「风险与依赖」把「必要时引入备份」当作可接受的兜底，本节原文把它当作必须避免的倒退，两处对同一风险处置不一致。统一为：引入索引备份是「受控回退」，触发条件 = 实测重建时长超过所属档位目标；回退后须重新评估存储成本。

七个容易被漏算的成本项：

  1. 上下文前缀的 LLM 成本（04 §5.2）：每次索引构建都要为每个 chunk 调用 LLM 生成前缀。这是全量重建时最大的单项 token 消耗，必须用 Prompt Caching 缓存文档级上下文，否则重建成本会显著超出预算（「超出一个量级」是方向性判断，非实测值，性质为阈值待实测；且 Prompt Caching 只能省输入 token 的重复部分，输出 token 与调用次数无法靠缓存减少，见 §2.6.5 前提 1）。
  2. LLM-as-Judge 的评测成本（07 §3.3）：判官调用量 = 评测集规模 × 每次评测的 claim 数 × 偏差控制的重评次数（位置偏差需交换顺序各评一次，即 ×2）。若回归集作为合并门禁（07 §2.5），这笔成本按 MR 频次发生。
  3. 双索引期间的成本翻倍（04 §5.6）：模型迁移期存储与写入同时翻倍，必须限定迁移窗口长度。
  4. 审计日志存储（无上界增长）：§2.6.5 规定审计日志异地归档、仅追加、不可重建，05 §9.3 的字段含 query_text（原始 + 扩展查询全文）、retrieved_chunks（列表 + 分数）、generated_claims（claim 全文 + evidenceIds）。这是每次交互都写入、含长文本、保留期通常数年不删的数据，增长曲线与向量库完全不同（向量库随知识量增长且可通过 06 §2.4 淘汰收敛，审计日志随交互量线性增长且不可收敛）。驱动因子：日均交互数 × 单条审计记录平均字节 × 保留期天数 × (1 + 异地副本数)，另加异地同步带宽。
  5. 漂移检测的语义过滤成本：06 §2.2 的 matches_semantic_filter(changed_hunks, entry.knowledge_type) 若用 LLM 实现，成本 = active 条目数 × 日均源变更命中率 × 单次过滤成本，每日发生。这可能超过判官成本（判官只在 MR 时发生）。06 未说明该过滤器是确定性规则还是 LLM——若为 LLM，须先做规则预筛再调模型。
  6. 激励回流看板的聚合成本（§2.4 原则 3）：从审计日志聚合「按作者/Owner 的命中与引用次数」需要持续扫描 retrieved_chunks 与 generated_claims，是审计日志的二次全量读取。驱动因子：审计日志扫描量 × 聚合频率。
  7. 反馈闭环的脱敏与聚类成本：07 §2.3 的「正则 + NER 识别敏感实体」与「向量相似度 + 主题聚类」，若 NER 与 Embedding 用模型实现，则成本 = 日均反馈数 × (NER 单次 + Embedding 单次)。07 §2.3 把这一步标为「全自动」，容易被误读为零成本。

成本约束应反向影响设计：若治理人力成本不可承受，说明 04 §3.5 的复核周期过密或知识条目过多，应通过 06 §2.4 边际价值评估收敛规模，而不是降低复核标准。

  • 「治理层是薄的」这个判断只在代码量意义上成立，在人力意义上不成立，必须分开说：治理层的代码确实薄（元数据 Schema + CI 脚本 + 审核流），但治理层的持续人力是 §2.6.6 三类成本中唯一不可收敛的一类（审核、漂移处理、冲突裁决、复核、激励看板运维、归因盲评），而 §4 更进一步指出「权限映射清洗在实践中经常超过整条摄入链路的开发量」——权限映射正是治理控制面的一部分。原文用「治理层是薄的」论证「自建成本可控」，与同一文档的 §4 和 §2.6.6 直接冲突。修正后的判断依据是：治理层自建的成本主要是持续人力而非一次性开发量，因此选型时真正要问的是「该产品能否承载这些治理动作」，而不是「自建要写多少代码」。
  • 若选择云托管服务，必须在选型阶段验证三件事：能否写入自定义元数据字段、能否在检索前做权限过滤（pre-filtering）、能否返回稳定的 chunk 标识。任一项不满足，本方案的关键控制就无法落地。
  • 若选择开源平台，须额外验证四项（比笼统的「治理生命周期缺失」可操作）：能否表达 status 四态状态机（06 §2.1）、能否存储并校验自定义 frontmatter、能否接入外部 CODEOWNERS 作为 Owner 来源、能否输出稳定的 chunk_ref。

2.7 验收指标与校准参数

蓝图 §10.4 明确门禁分级是本节的核心：只有性质为"机制保证"的指标可以在 P0 直接作为硬门禁；"阈值待实测"的指标在校准完成前只能观测，不得阻断。

4. P0 人力估算

蓝图 §10.2 明确本方案不给数字，只给最易低估的三项。任何具体人日数都必须先做小样本实测再外推，因为下面三项的规模完全取决于本团队存量状态。

实测方法（三步法）——原文写「按 §2.7.2 的方式」，但 §2.7.2 是「指标 → 目标值 → 校准方法」的参数校准表，不含任何人力估算方法（该引用错误继承自主文档 §10.2 的「按 §10.4 的方式」，两处一并修正）：

  1. 抽取 30–50 篇代表性存量文档做完整解析，统计实际人均耗时与脏数据比例，按形态分类（扫描版 PDF / 表格截图 / 失效内链 / 正常 Markdown）。
  2. 抽取 1–2 个 IAM 组做完整 acl_groups 映射，统计每组耗时与需人工裁决的授权冲突比例。
  3. 邀请 2–3 名业务专家标注 10 条金标样例，统计人均每条耗时与仲裁比例。

三项各乘存量规模并加风险系数（系数待实测）后外推。**任何跳过 ①②③ 的人日数字都不成立。**这三步已列入 §3.1 P0 建设项，与 C0 的形态调研同期。

  1. 存量文档的脏数据比例——§2.7.2 中"解析成功率 ≥ 95%"是目标值而非现状，首轮实测通常远低于此，返工量由脏数据形态（扫描版 PDF、表格截图、失效内链）决定。
  2. 权限映射清洗——把现有 IAM 组结构映射为 acl_groups（05 §9.1）的工作量，取决于历史授权是否已经混乱；这一项在实践中经常超过整条摄入链路的开发量。
  3. 金标集标注——需要业务专家时间，平台组无法自己完成（07 §3.2），且专家时间是全项目最稀缺的资源。

培训与上手：

  • 不需要培训"怎么用知识库"。用户侧入口是 Agent，用户感知不到知识库存在——这正是 05 §10.1 接口设计的意图。若需要培训用户，说明接口设计失败了。
  • 需要培训的是 Owner 侧：frontmatter 必填字段、复核触发条件、漂移告警的处理动作。
  • 上手成本判据：一个新 Owner 能在不查文档的情况下完成"收到漂移告警 → 确认 → 更新条目 → 合并"的闭环。做不到说明模板或告警文案有问题，应改工具而不是加培训。

注意：本节刻意不给出任何人日数字或激励系数。P0 人力必须实测；三项易低估点是定性提示，不是可直接引用的估算系数。（此条限定来自主文档 §10.2，此前在拆分时丢失。缺了它，上面三项很容易被当成估算系数使用——例如把"权限映射经常超过摄入链路开发量"直接引用为"权限 = 摄入 × 1.5"。）
