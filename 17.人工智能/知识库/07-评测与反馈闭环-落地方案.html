07 · 评测与反馈闭环 · 落地方案

对应蓝图 §8。本文解决：如何度量知识体系的效果？如何从失败中持续改进？

状态：草案（E2.3 / E3.2 / E3.3 / E4.2 / E5.2 / E6.2 / E7.1 待确认）

前置依赖：05-知识检索与引用（审计日志，须先补 §2.3 所列反馈埋点字段）· 04-知识存储（chunk_ref 内容寻址）

关联文档：06-知识维护与治理（边际价值）· 02-知识验证（冲突检测）· 08-约束执行（工程基线数据来源）· 09-度量评价与落地路径（评测体系排在 P2）

1. 定位与边界

评测与反馈闭环是知识库的"质量仪表盘"：它不生产知识，也不直接改进知识，但它决定哪些知识值得保留、哪些改进方向最有价值。

与 06 的分工：06 通过边际价值评估"这条知识是否值得维护"，本文通过评测集评估"这套知识体系整体是否有效"。

与 05 的分工：05 §9.3 提供审计日志原始数据，本文将其加工为可度量的指标与可归因的改进信号。

数据源缺口（阻塞项）：05 §9.3 与蓝图 §6.6.3 定义的审计字段为 trace_id / actor / query_text / permission_set / retrieved_chunks / filtered_out_count / generated_claims / rejected_claims / refusal / latency_breakdown / index_version / degradation_flags——其中没有「点踩」「重复追问」「转人工」「人工纠正」「代码回滚」「人工介入时长」任何一项。而 §2.3 六步流水线的全部输入信号、§2.4 的成本类指标、06 §2.4 边际价值的「命中有效率」都依赖它们。

因此本文所有涉及这些信号的指标均标注**「需新增埋点」**，且埋点是本文的 P0 前置条件而非可选优化。已在 05 §9.3 增补的字段：user_feedback（thumbs_down / repeat_ask / escalate / manual_correction / rollback）与 human_in_loop_ms。采集点在 MCP Server 侧还是 IDE/CLI 侧属待决策项（E7.1），因为它决定了能否覆盖「不经过 MCP 的本地交互」。

唯一不需要新增埋点的项是「条目命中次数 / 引用次数」（可由 retrieved_chunks 与 generated_claims 直接统计）。原表述「数据源已存在，无需新增埋点」只对这一项成立，不得推广到整个反馈闭环。

2. 核心设计决策

2.1 四层失败归因

蓝图 §8.1 定义四层失败类型，归因顺序是串行的：必须先排除上一层，才能归因到下一层。

类型诊断问题判定方法
Retrieval Failure正确证据是否进入 Top-K金标集比对：expected_citations 是否出现在检索结果
Generation Failure证据正确但答案是否错误证据已在 Top-K，但输出的 claim 与证据矛盾或未被证据支持
Business Understanding Failure是否误解术语、角色、版本或约束证据正确、答案表面通顺，但违反了 05 §6 受控术语表、06 §2.1 版本裁决或适用范围
Execution Failure代码、测试或工具操作是否错误知识正确传达，但生成的代码/命令/工具调用不通过编译、测试或 08 §3.1 Hook 校验

归因纪律：

  • 若正确证据未进 Top-K，即使答案也错，也只记 Retrieval Failure（避免一次检索失败被重复计入多类，导致改进优先级误判）。
  • 同一样例允许记录一个主归因 + 多个次归因，统计改进收益时只按主归因计数。

三处口径更正说明：

  1. 「Review 缺陷数」的数据来源不可能是 03：03 §4.1 的五维清单是知识条目审核标准，而该指标度量的是代码 Review 缺陷，两者不是一回事。原文把 03 §4.1（CODEOWNERS 配置）当作数据来源属双重错配。
  2. Change Lead Time 的 DORA 口径是 commit → production deployment，不是「需求提出 → 上线」（后者是 feature/flow lead time）。两者差值可能很大，混用会让「时效」类指标失去横向可比性。
  3. 「回滚率」不是 DORA 指标，且原表以 MR 为单位。DORA 的对应项是 Change fail rate 与 Deployment rework rate，均以部署为单位。已替换为 Deployment Rework Rate。
  4. 分类错位更正：原表把「缺陷逃逸率、回滚率、Review 后提交轮次」归入「效率」。按 DORA 的 throughput / instability 划分，它们属稳定性/质量，与效率方向相反——把它们算作效率会在报表上产生「稳定性变差但效率变好」的误导。

为什么「不预设提升百分比」是刻意设计：公开复盘确实报告了产出规模数字（例：OpenAI "Harness Engineering"，openai.com/index/harness-engineering/，2026-02 发布；第三方转载称约 5 个月 / 约 100 万行 / 约 1500 PR，该组数字本文不作为依据引用，仅说明此类外部数字存在）。但这些数字来自特定团队、特定代码库、特定时间窗，把外部数字抄成本团队的验收线，等于用一个无法验证的承诺替代基线测量。

2.5 回归集门禁分级

蓝图 §8.5.4 明确不对所有变更设硬门禁（过严等于没有），按变更类型分级：

变更类型回归集角色理由
检索参数调整（k、Top-K、rerank 阈值）硬门禁，不通过不得合并直接影响 Recall@K，且可快速验证
Embedding 模型升级硬门禁 + 双索引对比（04 §5.6）影响全量向量，回滚成本高
切分策略变更硬门禁影响 chunk_hash 与全部引用可解析性
单条知识内容修订软门禁，失败仅告警单条变更影响面小，硬门禁会拖慢知识更新
知识条目新增软门禁：跑受影响域的金标子集，Recall@K 下降超阈值则告警并要求 Owner 确认原表述「新增不影响既有召回」在检索原理上不成立：新增 chunk 会直接进入 Top-K 竞争（可能把原本正确的证据挤出窗口）、改变 BM25 的 IDF 统计、改变 RRF 名次，因此必然可能改变既有金标样例的 Recall@K。「除非引入重复」只覆盖其中一种情形，而重复拦截与召回位移是两类不同风险，须分别处置。用「回归集存在的理由」论证「不需要回归集」构成循环论证

3. 实施细节

3.1 金标集标注流程

四条纪律：

  1. query 必须来自真实场景，不得由开发者凭想象编写。想象的 query 分布与线上分布差异极大，用它调出的参数在线上无效。
  2. 标注「期望证据」而非「期望答案文本」。答案文本会随模型与知识修订变化，证据引用（chunk_ref）相对稳定。这也是 05 §7.1 采用内容寻址的直接受益方——若 evidence_id 用 chunk 序号，每次重新切分都会让金标集作废。
  3. 不可裁决的 query 必须丢弃并记录原因。强行保留会让评测结果长期噪声化。歧义原因本身是知识缺口的信号，应回流到 §2.3 反馈闭环。
  4. 知识变更后触发重标：被引用条目 deprecated 或 source_revision 变更时，相关金标样例进入复审队列，否则评测集会静默过期。

3.2 标注一致性度量

双人标注必须量化一致性，否则「一致」只是主观判断：

标注对象一致性指标说明
期望证据集合Krippendorff's Alpha（MASI 或 Jaccard 距离）这是集合型（多标签）标注，不是类别型。Cohen's Kappa 只适用于恰好 2 名标注者 + 单一名义标签，直接用于集合型数据无定义。若必须用 Kappa，须先按候选 chunk 逐项二值化再计算
归因层级（§2.1 四层）仅对主归因计算 Cohen's Kappa；次归因用 Alpha + 集合距离单独统计§2.1 允许「1 个主归因 + N 个次归因」，标注结果是集合型而非单一互斥类别，对整体直接算 Kappa 与 §2.1 的设计不自洽
答案质量评分加权 Kappa 或 ICC有序等级评分，需加权

标注者人数与指标选择必须匹配：§3.1 引入「第三人仲裁」后标注者为 3 名，Cohen's Kappa 已不适用（它只定义在 2 名标注者上），须改用 Fleiss' Kappa 或统一用 Krippendorff's Alpha。本方案统一用 Alpha，避免同一份数据混用两种系数。

Kappa / Alpha 低于阈值时，先修标注指南再重标，不得直接进入仲裁。指南不清导致的分歧会持续产生，仲裁成本远高于重写指南。

初始参考区间（来自方法学惯例，正式门槛仍须实测）：Cohen's Kappa 0.61–0.80 视为可接受、> 0.80 良好；Krippendorff's Alpha ≥ 0.80 可用、0.667–0.80 须说明理由。

小样本与类别不平衡陷阱：§2.2 的评测集初期只有 100–300 条、分八类，单类可能只有十几条。Kappa 在样本量小、类别极不平衡（prevalence problem）时估计极不稳定，同一批数据换个分布就能从 0.4 跳到 0.9。因此必须同时报告 PABAK 或分类别一致率，并规定每类最小标注样本量，否则「达标 / 不达标」的判定本身不可信。

3.3 LLM-as-Judge 的偏差控制

蓝图 §8.5.3 列出五类偏差及控制手段：

偏差表现控制手段
位置偏差倾向选择靠前/靠后的候选交换顺序各评一次，结果不一致则记为「判官不确定」
长度偏差倾向认为更长的答案更好评分维度中显式排除长度；提供等长对照样例
自我偏好倾向认可同族模型生成的内容判官模型与生成模型不同族
权威腔偏差措辞自信即判为正确判官只看「claim 是否被 evidence 支持」，不评措辞
格式偏差结构化输出得分偏高评分规则中固定格式权重为零

判官必须先通过人工一致性校准：取一批已有人工标注的样例，计算判官与人工的一致性（按 §3.2 用 Krippendorff's Alpha）。判官一致性未达标前，其产出的指标只能观测，不得作为门禁——这与蓝图附录「阈值待实测」的处置一致。

判官模型与 rubric 必须版本化，升级须重跑校准集：

要素规定理由
判官模型版本锁定到具体版本号，写入每次评测 run 的元数据判官升级会让历史指标不可比，不锁版本就无法判断指标变化来自知识改进还是判官漂移

「判官不确定」比例设上限（待实测）；超限则该批结果作废，先修 rubric位置偏差控制手段（交换顺序各评一次）会产生大量不确定样本，无上限则评测退化为抛硬币
不同族模型不可得时的降级允许同族判官，但其结果只能观测，永久不得作为门禁§3.3 的自我偏好控制手段失效时，不能假装它仍然有效
