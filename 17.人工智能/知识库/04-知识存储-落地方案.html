1. 概述

知识存储解决：审核通过的知识如何结构化存储、切分、索引？

知识库建设为多层知识控制系统，向量库只作为可重建的派生索引——删除索引不应导致知识丢失，索引损坏后应能从权威源（Git 仓库）重建。

2. 多层知识控制模型

派生索引原则：L4 层（向量索引、全文索引）均可从 L0 层（Git 仓库）完全重建。备份策略：索引不备份，只重建。

3. 元数据 Schema

3.1 P0 最小 frontmatter（7 字段）

---
status: active              # draft | active | deprecated | revoked
source_uri: gitlab://ocp/payment/src/main/java/com/ocp/pay/RefundService.java
source_revision: 8f31c92a4b
owner_group: ocp/payment-team
classification: internal    # public | internal | confidential | restricted
knowledge_type: Contract    # Concept | Decision | Policy | Procedure | Contract | FAQ | IncidentLesson
title: "退款接口的幂等键约束"
---

knowledge_type 为何是必填而非派生：分级复核周期（本文 §3.5）、漂移语义过滤（06 §2.2）、主张抽取范围（02 §4.4）都以它为输入。留到后期采集会让这三项机制在 P0 全部退化为无差别处理，而回填需 Owner 逐条判断——采集成本随时间单调上升。

3.2 自动派生字段

派生字段来源与规则
knowledge_id文件路径 docs/knowledge/{module}/{topic}.md → KB-{MODULE}-{TOPIC}，一经分配不再变更
content_hash对 git blob 计算：git show {source_revision}:{path} | sha256sum（不对工作区文件计算）
revision_id{source_revision} + {content_hash[:12]}，用于索引版本对齐
effective_fromgit log 中该文件的首次提交时间
effective_toactive 期间恒为 null；仅在转入 deprecated / revoked 时写入
review_due_ateffective_from + 该知识类型的复核周期（分级）
stewardfrontmatter 显式声明；未声明时回落 CODEOWNERS 派生，但必须写回固化
flags / flagged_atCI 写入的异常标记，人工不得手改

3.3 content_hash 必须基于 git blob

对工作区文件直接计算 SHA-256 会因换行符双轨（CRLF vs LF）和格式化器（Prettier）产生全量误报。hash 输入必须统一为规范化后的仓库字节：

# 入库时记录
git show {source_revision}:{path} | sha256sum
# 漂移检测时比对（同一条命令，天然免疫 CRLF 与编辑器差异）

3.4 effective_to 不能取「末次提交时间」

一条 active 知识没有失效时间。若把 effective_to 派生为「git log 末次提交时间」，则每条知识在被派生的那一瞬间就已落在有效区间之外，导致版本裁决规则与派生规则互相击穿。

statuseffective_to裁决含义
draftnull未生效，不参与裁决
activenull开区间，持续有效
deprecated进入 deprecated 的时间已过 sunset 起点，仍可召回但需告警
revoked撤销时间硬失效，任何情况下不得进入召回集

3.5 复核周期按风险分级

知识类型 / 风险复核周期超期后果
安全、合规、资金、权限（restricted）30 天verification_overdue + 高优先级告警
Contract（接口、表结构、配置）60 天verification_overdue + 召回时附过时警告
Procedure、Policy90 天verification_overdue

3.7 字段字典（跨文档字段的唯一登记处）

本文是元数据 Schema 的唯一权威。05 / 06 在各自文档中使用了若干本文原先未登记的字段——字段定义分散在使用方会造成 Schema 双头：两个文档各自演进后必然分叉，索引 Pipeline 与 CI 校验也无法据本文生成完整校验规则。下列字段统一在此登记。

登记规则：任何文档新增 frontmatter 或索引字段，必须先在本表登记（字段名 / 类型 / 取值域 / 写入方 / 引入阶段），再在使用方文档中引用。未登记的字段 CI 校验按 Error 处理。

3.7.3 字段字典的三项约束

  1. expires_at 与 effective_to 不是两个字段。本文 §3.2 用 effective_to，06 §2.1 用 expires_at，语义完全相同（有效区间右端点）。统一为 effective_to，06 侧的 expires_at 视为别名，CI 校验时归一化——否则同一条知识会出现两个右端点，裁决第 4 条无法执行。
  2. applies_to 在 P0 为可选，但 Contract 类在 P1 起必填。06 §2.1 裁决第 1 条（适用范围匹配）是七条中的第一条，缺 applies_to 时该条恒为「无法判定」，裁决直接落到第 7 条 conflicted——即没有 applies_to 的版本裁决机制是不成立的。
  3. flags 的写入方唯一性是 S1.5 的实质内容，与存储位置（Git frontmatter vs 元数据库）无关。无论 S1.5 选 A 还是 B，都必须由 CODEOWNERS + CI diff 校验保证人工不可手改。

5. 索引 Pipeline

5.1 Chunk 切分规则

  • 按语义边界切分，不得纯定长：H2 > H3 > 段落 > 句子
  • 单个 H2 章节超出 token 上限时才在段落边界二次切分
  • 表格与代码块作为不可分割单元（超长表格按行组切分并重复表头）
  • 初始参数：300-500 tokens / 重叠 50 tokens（必须按文档类型分别实测）

5.2 上下文前缀（关键技术）

在把 chunk 送去向量化之前，先拼接一段说明「这个 chunk 在整篇文档中处于什么位置」的前缀：

原始 chunk：
  「该接口已废弃，请改用 v2。」

加前缀后送 Embedding：
  「本片段来自《支付域 - 退款接口契约》，
    描述 refund/v1 接口的生命周期状态。
    该接口已废弃，请改用 v2。」

前缀同时进入 Embedding 与 BM25 两个通道。若只对向量通道加前缀，BM25 通道仍检索脱离上下文的裸 chunk，混合检索的收益会被抵消一半。

5.3 每个索引 Chunk 的元数据

5.4 Embedding 模型选型要点

考量要求说明
中英混合必须企业知识普遍中英混杂
代码语义建议知识条目含代码引用
最大输入长度≥ chunk 上限 + 前缀长度前缀会挤占有效长度
维度与向量库成本权衡维度越高成本越高
版本可锁定必须模型升级会改变向量空间

不得直接使用未评估的模型：必须用评测集实测后再定。不接受榜单排名作为选型依据。

5.5 向量存储选型

方案适用场景主要代价
Elasticsearch / OpenSearch已有 ES 集群，BM25 与向量同库向量检索性能弱于专用库
Milvus大规模（千万级）、独立扩缩容多一套存储运维
Qdrant中等规模、重视过滤性能生态较新
pgvector已有 PostgreSQL、向量量级不大大规模下性能受限

选型的决定性因素是过滤性能：检索前按 classification 与权限过滤是每次查询都带的高选择性过滤条件。必须选用支持 filtered ANN（pre-filtering）的方案。
