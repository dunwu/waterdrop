1. 定位与边界

维护与治理覆盖知识"入库之后、下线之前"的全部动作：版本裁决、漂移检测、影响分析、Sunset 生命周期、边际价值评估。它不解决"知识如何产生"（→ 01）或"知识如何被使用"（→ 05），只解决"知识如何保持可信"。

与 03 的分工：03 §3.1 定义"谁负责"（Owner 团队制 + Steward 派生规则），本文定义"做什么、何时做、做到什么程度"。

角色归属更正：原表述称 03 定义了「Owner / Steward / 园艺」三个角色，实际 03 全文没有「知识园艺」这一角色。该角色的职责定义在本文 §3.5，其在四类分工中的归属见 09 §2.4。此处保留说明是因为角色清单不一致会直接影响 CODEOWNERS 与告警接收人配置。

与 02 的分工：02 在 MR 合并前拦截格式与引用错误（单次），本文在 MR 合并后持续监控知识是否仍然正确（连续）。

2. 核心设计决策

2.1 版本裁决：七条规则 + 五级权威源

蓝图 §7.1 给出七条裁决顺序，不能简化为"按修改时间"。落地为 scripts/version-arbiter.py，输入两条主张，输出胜方与理由。

依据与置信度：本节与 §2.2 的语义过滤信号清单、§2.4 的边际价值量纲统一，在蓝图附录中均标注为自拟 / 方向性依据——即它们是工程推导结论，没有外部标准或公开实测数据支撑。落地时须按 09 §7 的校准计划实测后再固化，不得在评审中把它们表述为业界通行做法。

2.2 漂移检测：语义过滤 + 告警聚合

直接按"源文件是否有新提交"判定漂移会产生 Owner 无法处理的告警量（格式化、注释改动、无关重构都会触发），最终导致告警被集体忽略——治理系统最典型的失效方式。

两级判定：

# scripts/drift-check.py
# 一次性建立 路径 → 最新 commit 的反向映射，避免逐条调 git
commit_map = parse( git log --name-only --pretty=format:%H -- {watched_paths} )

for entry in knowledge_entries(status == active):
    path = resolve(entry.source_uri)
    latest = commit_map[path]
    if latest == entry.source_revision:
        continue                                    # 未漂移

    # 零级：源文件已被删除 → 最高优先级，不走语义过滤
    # 必须在 diff 之前判定：文件删除后 git diff rev..latest -- path 返回空，
    # 语义过滤会把空 hunk 判为「无关变更」并静默推进 auto_rebase_to，
    # 导致「源已删除」被记录为「已是最新」，删除残留率因此不可能归零。
    if not exists_at(latest, path):
        report_drift(entry, kind = 'source_deleted', priority = 'high')
        continue

    # 一级：源文件确有变更 → 记录候选，不立即告警
    changed_hunks = git diff entry.source_revision..latest -- {path}

    # 二级：只有命中语义相关变更才升级为需处理漂移
    if matches_semantic_filter(changed_hunks, entry.knowledge_type):
        entry.flags += [drift_detected]
        entry.flagged_at = now()
        enqueue_alert(entry.owner_group, aggregate = daily_digest)
    else:
        entry.auto_rebase_to = latest               # 无关变更：静默推进基线

语义相关变更信号清单（按知识类型）：

知识类型判定为语义相关变更的信号
Contract（HTTP/RPC 接口）路径、方法、请求/响应 Schema、字段必填性、错误码变化
Procedure（操作步骤）函数签名、命令、配置项名称或默认值变化
Policy（架构/业务规则）规则涉及的类、注解、状态机分支变化
Concept（设计背景）仅当被引用的代码位置整体删除或迁移时才判定
全部类型源文件被删除 → 由 §2.2 伪码的零级分支直接判定为 source_deleted，升级为高优先级，不进入语义过滤（否则空 diff 会被判为无关变更）

明确不判定为漂移：纯空白与换行变化、Markdown 格式化、注释文字调整、日志文案修改、与知识主张无关的代码块变更。

告警聚合：按 owner_group 做每日摘要（daily digest），单个团队单日告警条数超过阈值时合并为一条汇总通知，不逐条推送。

2.3 flags 字段独立于 status

status 枚举固定为 draft | active | deprecated | revoked（04 §3）。漂移与过期是叠加在 status 之上的独立标记，写入 flags 数组：

flags: []        # 取值：drift_detected | verification_overdue | owner_missing | steward_missing | conflicted
flagged_at:      # ISO 8601，最近一次打标时间（CI 写入，人工不得手改）

一条知识可以同时是 status: active 且 flags: [drift_detected, verification_overdue]——"仍然生效但已待复核"正是治理最需要表达的复合状态。

owner_missing 与 steward_missing 必须是两个独立标记，因为它们是两种检查、两个时机、两种处置：

标记检查内容时机处置载体
owner_missingowner_group 在 GitLab 中不存在MR CI（同步）Error，阻断合并——新增孤儿知识率 = 0 的唯一机制载体03 §7 S3
steward_missingowner_group 存在，但派生不出 Steward（组内无满足资历条件的成员）每日定时扫描告警 + 由 owner_group 的 Owner 角色成员认领03 §6.2

原设计用同一个 owner_missing 承载两者，会把「组织调整窗口期的 Steward 空缺」升级为阻断无关 MR 合并的 Error——团队重命名或成员批量变动时，整个仓库的知识 MR 会被集体卡住。

机制成本须写进方案：owner_group 存在性校验依赖 GET /groups/:id，需要读 API 的 Token 与配额；组数多时应缓存（建议 TTL 1 小时）并处理 GitLab 可见性限制（私有组对 Token 不可见时会误判为「不存在」，须区分 404 与 403）。

2.4 边际价值：统一量纲到人时/年

蓝图 §7.7 指出原公式"价值分 − 成本分"量纲不同不可计算。改为统一量纲到"人时/年"：

年度价值（人时/年）
  = 年检索命中次数 × 单次命中节省的人时 × 命中有效率

  年检索命中次数     ← 05 §9.3 审计日志的 retrieved_chunks
  单次命中节省的人时 ← 实测：无知识库 vs 有知识库的定位耗时差
  命中有效率         ← 命中后未被点踩、且未触发返工的比例（07 §2.4）

年度成本（人时/年）
  = 年更新次数 × 单次更新人工耗时
  + 年复核次数 × 单次复核人工耗时

  年更新次数   ← git log 统计该条目的实际提交次数
  年复核次数   ← 由 04 §3.5 的分级复核周期决定
  单次耗时     ← 实测抽样

边际价值 = 年度价值 − 年度成本   （单位：人时/年）

模块关键度不进公式，而作为否决项（等级量无法与人时相乘）：

两个维度必须先有可执行定义，否则下表不可判定（§6 已把「模块关键度的分级标准」列为待实测项，但下表已经在用它做否决）：

  • 模块关键度：建议由 docs/knowledge/** 的目录级 _index.yaml 显式声明 criticality: high | normal，不做事后推断。理由是关键度是业务判断，无法从代码指标推导；由 Owner 在建立路由地图时一次性声明，成本最低且可审计。未声明的目录默认 normal。
  • 模块状态：建议用可计算代理量——该模块 source_uri 指向的目录在最近 N 个自然月内的非 bot 提交数。活跃 = N 月内有提交；活跃但低频 = 有提交但低于阈值；无活跃开发 = 无提交；模块已废弃 = 目录已删除或在 _index.yaml 中标记 archived。N 与阈值属待实测项。
边际价值模块关键度模块状态决策
正任意活跃正常维护
正任意活跃但低频保留，按 04 §3.5 降低复核频率
正高无活跃开发保留，标记为低频关键知识
正低无活跃开发保留，延长复核周期至上限
负高无活跃开发不归档，转人工评审（关键度否决）
负低无活跃开发连续观察期满后归档
负任意模块已废弃立即标记 deprecated，进入 Sunset

三重防误删保护（缺一不可）：

  1. 豁免类别：安全、合规、资金、权限相关知识不参与边际价值评估，永不自动归档。
  2. 关键度否决：边际价值为负但模块关键度高时不归档。
  3. 人工审核：任何归档动作必须经 Owner 审核，系统只产出建议清单。

观察期不可省略：边际价值基于历史统计，而知识价值有滞后性——一条事故复盘知识可能一年只被检索一次，但那一次避免的是重大故障。观察期内若命中一次高价值场景（如事故归因引用），统计窗口应重置。

本模型的三个输入目前都依赖尚未建成的能力，实施前必须逐项确认前置条件：

输入依赖当前状态前置条件
年检索命中次数05 §9.3 审计日志的 retrieved_chunks字段已定义审计日志保留期必须 ≥ 观察期长度。若 M4.4 取 180 天而合规确定的保留期短于 180 天，边际价值在数学上无法计算（RT1.4 因此不只是合规问题，也是本模型的硬约束）
命中有效率「命中后未被点踩、且未触发返工」❌ 无数据源05 §9.3 的审计字段中没有点踩 / 返工 / 人工介入任何一项，07 §2.3 已把它们标注为需新增埋点。埋点落地前，命中有效率只能取 1.0（等于不折算），须在报表中显式标注该假设
年更新次数git log 统计可计算须排除 bot 提交（见 §3.5 的自证循环风险）

「单次命中节省的人时」是两组对照实测，需要专门安排无知识库 / 有知识库的对照任务，成本不低且样本量小时方差极大。在该值实测出来之前，边际价值的绝对数值没有意义，只能用同一批条目的相对排序做归档建议——这一点必须写进 §3.5 的清单说明，否则 Owner 会把 -2.5 人时/年 当作可信数字。

2.5 Sunset 生命周期

接口废弃时进入 deprecated 状态，frontmatter 增量字段：

status: deprecated
deprecated_at:          # ISO 8601
replacement_api:        # 替代接口 URI
migration_guide:        # 迁移指南链接
sunset_at:              # 计划下线日期
known_consumers:        # 已知调用方清单
owner_group:            # 责任团队

Schema 归属：上述 6 个增量字段（deprecated_at / replacement_api / migration_guide / sunset_at / known_consumers / auto_rebase_to）已统一登记到 04 §3.7 字段字典。字段定义只在使用方文档中出现会造成 Schema 双头——04 自称是元数据 Schema 的唯一权威，若 Sunset 字段不在其中，索引 Pipeline 与 CI 校验都无法据 04 生成完整校验规则。

known_consumers 的数据来源必须明确：它不能靠人工维护（必然过期）。P1 阶段由 CODEOWNERS 反查 + 人工确认填充；P3 关系图谱（§3.4）上线后改为从 consumes 边自动派生，人工填写值仅作兜底。

四条控制要求：

  1. 新代码调用废弃接口时阻断（通过 08 §3.1 的 Hook 校验）。
  2. 存量调用按 sunset_at 时间告警。
  3. 文档和知识条目同步标记废弃。
  4. 删除前确认调用方和引用清零。

3.3 漂移检测 CI 定时任务

GitLab CI 的 job 定义中不存在 schedule: 关键字；定时流水线由 UI（Build → Pipeline schedules）或 API 配置 cron 表达式，YAML 里只能通过 $CI_PIPELINE_SOURCE == "schedule" 判断当前是否为定时触发。

# .gitlab-ci.yml
workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_PIPELINE_SOURCE == "schedule"'
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'

knowledge-drift-check:
  stage: validate
  rules:
    - if: '$CI_PIPELINE_SOURCE == "schedule"'   # cron "0 2 * * *" 在 Pipeline schedules 上配置
  script:
    - python3 scripts/drift-check.py --notify --aggregate=daily
  artifacts:
    paths:
      - drift-report.json
    expire_in: 1 week

artifacts: reports: 没有 drift 这个子键。其合法子键为固定枚举：accessibility / annotations / api_fuzzing / browser_performance / codequality / container_scanning / coverage_report / coverage_fuzzing / cyclonedx / dast / dependency_scanning / dotenv / junit / load_performance / metrics / requirements / sarif / sast / secret_detection / terraform。写 drift: 会在 CI lint 阶段直接报错，Job 无法创建。本节开头刚好指出了同类的 schedule: 错误，此处属同一类失误。

若需要在 MR 页面可视化漂移结果，可用的合法路径是 reports: annotations:（把漂移项渲染为行内批注）或 reports: dotenv:（把摘要作为变量传递给下游 Job）；仅归档报告文件则用上面的 artifacts: paths:。

3.4 影响分析：三源融合（蓝图 §7.5）

核心关系 kind（自定义扩展 Backstage）：

kind 归属说明（已更正）：Backstage Software Catalog 的原生 kind 只有 9 个——Component、API、System、Domain、Resource、Location、Group、User、Template。

上图节点是否为原生 kind正确建模方式
API / System / Domain✅ 是直接使用
Service❌ 不是建模为 Component，spec.type: service
Table❌ 不是建模为 Resource，spec.type: database（或 table）
Owner❌ 不是用 Group / User 表达，通过 spec.owner 关联，不新建 kind
CodeSymbol / Config / Feature / Document / Policy / Module / Asset / Job❌ 不是自定义 kind，须走 Backstage 的模型扩展机制注册

自定义 kind 的代价必须写进选型：Backstage 的核心插件（Catalog 页面、依赖图、TechDocs、Scaffolder 模板）只理解原生 kind，自定义 kind 在这些插件中不会被识别，需要自行开发前端展示与关系渲染。因此 M3.2「A. Backstage Catalog / B. 自研图数据库」的真实取舍不是「复用 vs 自建」，而是「复用原生 kind 的表达力 + 为自定义 kind 自建插件」vs「全自建」。

自定义 kind 一旦注册，必须固化 Schema 版本，不允许在关系图中隐式新增字段。

owner_group 格式转换：frontmatter 使用简写形式（如 ocp/backend），对接 Backstage Catalog 时由索引 Pipeline 转换为 {kind}:{namespace}/{name}（如 group:default/ocp-backend），两者不得混用。

关键约束：园艺 Agent 不得有自动删除权（蓝图 §7.7.3 三重防误删），只产出建议清单，由 Owner 与 Steward 人工决策。

周报必须覆盖全部 5 个 flags 取值（§2.3），否则治理清单长期漏掉两类最高风险的条目：

flags 取值是否进周报对应清单SLA逾期升级
owner_missing原设计已覆盖orphan_entries5 个工作日→ owner_group 的上级 Group Owner

verification_overdue原设计已覆盖expired_entries按 04 §3.5 分级周期→ Steward
drift_detected❌ 原设计缺失drift_entries5 天（§4「漂移未处理天数」）→ Owner + Steward
conflicted❌ 原设计缺失conflict_entries3 天（§4「冲突未决时长」）→ 按蓝图 §7.1 权威源等级裁决

去重与幂等：周报是周期产物，同一条目会连续多周出现。必须记录 first_flagged_at 与 report_count，并在清单中区分「本周新增」与「历史未处理」——否则 Owner 每周收到同一份长清单，第三周起就会整体忽略，这正是 §2.2 开头指出的治理系统典型失效方式。

low_value_entries 的机器自证风险：若 §2.5 的 auto_rebase_to 由园艺 Agent 自身提交，这些机器提交会被 git log 统计为「年更新次数」，从而抬高该条目的年度成本、压低边际价值，形成「园艺 Agent 越勤快、越多条目被判为低价值」的自证循环。规避方式：成本项的年更新次数统计排除 bot 账号提交（按 author_email 过滤）。
